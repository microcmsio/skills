## 0. データの受け取り方を決める

既定は、次の 2 つをファイルでもらう方法。依頼者に「何を、どうやって出すか」をこの表の形で伝える。

| もらうもの | 出し方（依頼者が行う） | 入っているもの |
|---|---|---|
| WXR | 管理画面の「ツール → エクスポート」で「すべてのコンテンツ」 | 全投稿タイプ（下書き・非公開・予約・ゴミ箱を含む）、ターム、著者、コメント（スパムを除く）、postmeta（ACF / SCF の値、SEO のメタ）、ACF / SCF の管理画面で作ったフィールドグループ（`acf-field-group` / `acf-field` 投稿） |
| `wp-content/uploads` | 管理画面からは取れない。レンタルサーバーのコントロールパネルのファイルマネージャーか FTP / SFTP で zip にする。既存のバックアップ（UpdraftPlus やサーバーの自動バックアップ）に含まれていれば、それでもよい | 画像・PDF などの実ファイル（元画像、縮小版、どこにも使われていないものを含む） |

WXR は `examples/wxr-to-json.mjs` で投稿タイプごとの JSON にする（postmeta のシリアライズも戻す）。`meta` は同じキーの値をまとめた参照用で、`metaEntries` は `{key, value}` の配列として元のレコード順と重複を保持する。1 レコードの配列値と同じキーの複数レコードを区別する必要がある場合は `metaEntries` を読む。出力先には空のディレクトリを使う。書き出しが途中で止まるほど大きいサイトは、投稿タイプごとに分けてエクスポートしてもらう。

WordPress.com や、メディアを外部のストレージに置くプラグインを使っているサイトには、uploads フォルダがない。添付ファイルに `_wp_attached_file` がない（`wxr-to-json.mjs` の `file` が空）か、URL が `/wp-content/uploads/` でなければこれに当たるので、uploads を頼まずに公開 URL から取得する（2 章）。uploads をまとめて出せない場合も同じ。メディアを zip にするプラグインを本番に入れる方法もあるが、入れるかどうかは依頼者が決める。

表示のための情報（テンプレートの文言、見た目の条件）は集めない（フロントエンドは作り直すため）。WXR を調べて次のことが見つかったときだけ、テーマ（`wp-content/themes/<使用中のテーマ>`）と `wp-content/mu-plugins` のコードを頼む。

- postmeta の `_<フィールド名>` にフィールドキー（`field_...`）があるのに、WXR のフィールド定義（`acf-field`）に見つからない。コードで登録しているか、名前を変えた名残。値の種類（画像の ID か、投稿への参照か）を確かめるのに要る
- 本文のショートコードや独自ブロックの意味が、公開ページの HTML を見てもわからない（独自テーブルや設定値を読んでいそうなもの）

WXR に入らないもの（`wp_options` の値、独自テーブル、プラグインの設定）も、棚卸しで見つけたら `plan.md` の「先に決めてほしいこと」に載せ、公開ページから読み取るか、移さないかを決める。フォームの送信内容や申込者のような個人情報は、移さない前提で確認する。

### 2 つで足りないとき

コードで大量のデータを組み立てている、独自テーブルが中心になっているなど、WXR と公開ページでは中身がわからないサイトは、WP-CLI が使える WordPress で読む。

- **手元に複製する**：本番の DB ダンプと `wp-content` をもらい、手元の WordPress 環境（Local、MAMP、XAMPP など、WP-CLI が使えるもの）に読み込む。URL は `wp-config.php` の `WP_HOME` / `WP_SITEURL` で手元向けに上書きし、DB の中身（`wp search-replace` など）は書き換えない。本文中の URL を本番のまま取り出すため。予約投稿の公開などが手元で走らないよう、`DISABLE_WP_CRON` も有効にする。書き出しのスクリプトは案件ごとに書く（`wp eval-file` で実行すると、`get_fields()`・`parse_blocks()`・`get_permalink()` など WordPress の関数がそのまま使える）
- **サーバー上で実行する**：本番かステージングのサーバーに SSH で入れて WP-CLI があるなら、そこで書き出しを実行する。本番に負荷がかかりファイルも置くので、実行してよいかと時間帯を必ず人に確認する

基本は WXR を使う。

## 1. 最初に確認すること

- もらえるもの：WXR、`wp-content/uploads`、（0 章の条件に当たるときだけ）テーマと mu-plugins のコード、（予備の手段として）DB ダンプ
- エディタ：Gutenberg / クラシック / ページビルダー（Elementor、Divi など）が混在していないか
- 入っているプラグイン：ACF・SCF・Meta Box などのカスタムフィールド系、SEO 系（Yoast、Rank Math、All in One SEO）、多言語（WPML、Polylang）、EC（WooCommerce）、フォーム。WXR の postmeta のキー（`_yoast_`、`_elementor_` など）や公開ページの HTML から推測できる
- 対象範囲：下書き・非公開・予約投稿、コメント、ユーザー、メニューを移すか

## 2. メディアの取り方

画像・ファイルは、もらった `wp-content/uploads` から読む（`upload-media.mjs --uploads <展開したフォルダ>`）。サイトにはアクセスしない。

- **上げる対象**は、使われているものだけ。WXR の添付ファイルのうち、アイキャッチ・カスタムフィールド・本文から参照されているものと、本文に直接書かれた画像（`<img src>`、`[gallery ids]`、`[caption]` など）を集める。縮小版や、どこにも使われていない画像は上げない
- **URL → ファイル**：URL の `/wp-content/uploads/` より後ろが uploads フォルダ内のパスになる（日本語のファイル名は URL デコードする）。旧ドメインや `http://` の URL でも同じ。縮小版（`-300x200`）の URL は、まずそのままの名前で添付ファイルを探し（元画像の名前に `-300x200` が付いていることがある）、なければ `-WxH` を外して探す。縮小版は元画像の名前から作られるので、外した名前は `-scaled` ではなく元画像（`original_file`）に一致することがある。そのときは、その添付ファイルの `file`（`-scaled`）に寄せ、同じ画像を二度上げない
- **2560px を超える画像**は、WordPress が縮小した `-scaled` が添付ファイルの本体（`_wp_attached_file`）になっていて、元画像は `_wp_attachment_metadata` の `original_image` にある（`wxr-to-json.mjs` が `file` と `original_file` に出す）。既定は `-scaled` を上げる
- **uploads にないファイル**（移行元でも消えている）と、**uploads 以外の URL**（外部サービス、S3 や CDN に置くプラグイン）は、`media-skipped.json` に出る。外部の URL は公開 URL から取るか、人に確認する
- uploads をもらえないときだけ、公開 URL から取得する（`--uploads` を付けない）。Basic 認証や IP 制限、WAF で弾かれることがある

## 3. 構造の洗い出し

次の一覧を作り、`plan.md` に件数つきで書く。

- 投稿タイプ・状態ごとの件数：`wxr-to-json.mjs` の `counts.json`
- タクソノミーとタームの数：`terms.json`
- postmeta のキーと件数：全投稿の `meta` のキーを数える
- 投稿タイプ・タクソノミー・フィールドの定義：WXR のフィールド定義と値の形、公開ページから読み取る。コードをもらった場合は下記も探す

WP-CLI が使える場合は `wp post-type list`、`wp taxonomy list`、`wp post list --post_status=any --format=count`、`wp plugin list` でも確かめられる。

コードで探すもの：

- `register_post_type` / `register_taxonomy` — 投稿タイプ・タクソノミーの定義
- `acf_add_local_field_group`、`acf-json/` フォルダ — コードで定義された ACF フィールド
- `add_shortcode` — ショートコードの定義と、それが何を出力するか
- `add_filter('the_content'` など — 表示時に本文を加工している処理
- `$wpdb->prefix` を含むクエリ、`CREATE TABLE` — 独自テーブル
- `get_option` / `update_option` — 設定値
- `mu-plugins/` — 必ず見る

コードに定義があるのに WXR に件数がない投稿タイプ（`can_export` を無効にしているものなど）や、WXR にあるのにコードに定義がない投稿タイプ（削除したプラグインの名残）にも気をつける。

## 4. 本文の扱い

### Gutenberg

生の本文（`<!-- wp:xxx -->` コメント付き）を、ブロック単位に分けてから変換する。Node なら `@wordpress/block-serialization-default-parser` の `parse()` が、PHP の `parse_blocks()` と同じ結果を返す。表示用 HTML だけから変換すると、どのブロックだったかの情報が消える。

同じブロックでも、書かれた時期の WordPress のバージョンで HTML が違う（見出しの `wp-block-heading` クラスの有無、古いギャラリーの `blocks-gallery-grid`、リストの `list-item` ブロックの有無など）。変換は、ブロック名と属性を見て書き、HTML の形には頼りすぎない。

ブロックの種類ごとの変換先は `richeditor.md` の対応表を使う。対応表にないブロック（`core/columns`、`core/embed`、独自ブロックなど）は、件数を数えて `plan.md` の「先に決めてほしいこと」に載せる。

`<!-- wp:block {"ref":123} /-->` は再利用ブロック（`wp_block` 投稿）への参照。中身を展開してから変換するか、共通パーツとして別 API にするかを決める。

### クラシックエディタ

本文に `<p>` が付いていないことがある。WordPress は表示時に `wpautop()` で段落を付けている。変換前に段落を付けること（Node なら `@wordpress/autop` の `autop()`）。Gutenberg の本文の中に、ブロックコメントのない HTML（クラシックブロック）が混ざっていることもある。

`[caption]...[/caption]` は画像＋キャプションのショートコード。`figure` + `figcaption` に変換する。

### ショートコード

全部のショートコード名を数える（正規表現 `\[([a-zA-Z0-9_-]+)` で本文を走査）。それぞれ次のどれにするかを決める。

- 静的な HTML に展開する（属性だけで出力が決まるもの）
- 別フィールドに逃がす（ボタンなど、構造として残したいもの）
- 消す（不要になったプラグインのもの）
- 記録して人が直す

**独自テーブルや設定値を読むショートコード**（例：料金表）は、本文だけ見ても中身がない。コードを読んで、データの出どころまで確認する。

### ページビルダー

Elementor のデータは本文ではなく postmeta（`_elementor_data`、JSON）にある。セクション単位で microCMS の繰り返しフィールドに対応させる。ウィジェット 1 種類ごとに型を作ると数が爆発するので避ける。表示用 HTML からの変換は情報が欠けるので、人の確認が必須。

## 5. カスタムフィールド（ACF / SCF）

ACF と Secure Custom Fields（SCF。ACF から分かれたもの）は同じ形式で postmeta に保存する。日本で多い Smart Custom Fields は別の形式（同じキーに複数の値、定義は `smart-custom-fields` 投稿）なので、下の表は当てはまらない。WXR から読むときは、次の形式を自分で組み立て直す（`wxr-to-json.mjs` はシリアライズを戻すところまで）。

| フィールド | postmeta の形 |
|---|---|
| テキストなど | `client` = 値、`_client` = `field_xxx`（フィールドキー） |
| 画像・ファイル | 添付ファイルの ID（URL ではない） |
| ギャラリー | 添付ファイル ID の配列（シリアライズ） |
| リピーター | `members` = 行数、`members_0_name`、`members_0_role`、`members_1_name`… |
| フレキシブルコンテンツ | `sections` = レイアウト名の配列（シリアライズ）、`sections_0_heading`… |
| 関連（投稿オブジェクト・リレーションシップ） | 投稿 ID（または ID の配列） |
| オプションページ | `wp_options` に `options_<name>` で保存 |

フィールドグループの定義から、各フィールドの種類と入れ子を一覧にする。定義は 3 か所にあり得るので、全部見る。

- 管理画面で作ったもの：WXR の `acf-field-group`（グループ）と `acf-field`（フィールド。`post_parent` がグループかリピーターなどの親フィールド、`post_excerpt` がフィールド名、`post_name` がフィールドキー）。設定は本文にシリアライズされていて、`wxr-to-json.mjs` が `settings` に戻す
- コードで登録したもの：テーマやプラグインの `acf_add_local_field_group()`
- `acf-json/` フォルダ（テーマ内）の JSON

postmeta の `_<フィールド名>` に入っているフィールドキーで、値と定義を結びつける。定義が見つからないキーは、まずテーマと mu-plugins のコードを頼む（0 章）。コードにもなければ、名前を変えたか削除したフィールドの名残とみなし、値の扱いを人に確認する。microCMS への対応は `microcms.md` を参照。

WP-CLI が使える場合は、PHP の `get_fields($id)` で整形済みの値が取れる。リピーター・フレキシブルコンテンツの行もフィールド名がキーになり、画像は ID と URL を含む配列になる。`get_fields($id, false)` は整形しない値を返すが、行の中のキーがフィールドキー（`field_xxx`）になるので、変換には向かない。

## 6. DB に残っていない・別の場所にあるデータ

洗い出しの段階で必ず探す。

- **本文に表示時だけ足されている内容**：`the_content` フィルターや、本文中のショートコード・動的ブロックの出力。種類の違う記事を数件選び、公開ページ（`curl <permalink>`）の本文部分と、生の本文に段落を付けたものを比べると見つかる。テンプレートに直接書かれた文言など、本文の外にある表示の情報は対象外（0 章）。
- **独自テーブル**：プラグインやテーマが作ったテーブル。必要なら別 API として移す。
- **設定値**：`wp_options` のシリアライズされた配列（会社情報、SNS リンクなど）。microCMS のオブジェクト形式 API に移すのが自然。
- **メニュー**：`nav_menu_item` 投稿。microCMS では設定用のオブジェクト形式 API にするか、フロントエンドの設定に持つ。
- **SEO**：Yoast（`_yoast_wpseo_title`、`_yoast_wpseo_metadesc`）、Rank Math（`rank_math_title`、`rank_math_description`）など。プラグインごとにキーが違う。
- **フォーム**：プラグインが出力しているものは移せない。フロントエンドで作り直す前提で一覧にだけ載せる。

## 7. よくある落とし穴

- 画像 URL が縮小版（`photo-300x200.png`）を指している。引き方は 2 章。
- 画像 URL がステージング環境のドメインや `http://` を指している。
- 著者を表示名でつなぐと、同姓同名や改名でずれる。ログイン名（WXR の `dc:creator`）でつなぐ。
- HTML エンティティ（`&amp;`、`&#8217;` など）がタイトルに残る。デコードする。
- 予約投稿・非公開の扱いを決めずに流すと、公開されてはいけないものが公開される。
- 日付のタイムゾーン。`post_date`（サイトの時刻）と `post_date_gmt`（UTC）を取り違えない。扱いは `general.md` の「既定の扱い」。microCMS にはタイムゾーン付きの ISO 8601 で送る。サイトのタイムゾーンの設定は WXR に入らないので、公開済みの記事の `post_date` と `post_date_gmt` の差で判断する（0 なら UTC のまま、+9 時間なら日本時間。下書きの `post_date_gmt` は `0000-00-00`）。差が 0 だったら、そのことを `plan.md` に書く。
- 日本語のスラッグ。スラッグを付けずに公開した記事は、`post_name` に日本語が URL エンコードされた形（`%e3%81%8a…`）で入っている。microCMS のコンテンツ ID には使わない（ID は `post-123` の形）。新サイトの URL で日本語のスラッグを残すか（デコードして使う）、英数字で付け直すか（リダイレクトが要る）は、`plan.md` の「先に決めてほしいこと」に載せる。リダイレクト表の旧 URL は、エンコードの大文字・小文字の違いでも一致しなくなることがあるので、設定先でどう照合されるかを確かめる。
- 本文中の画像の `alt` が空でも、メディアライブラリ側（`_wp_attachment_image_alt`）には代替テキストが入っていることがある。空なら添付ファイル側の値で補う。
