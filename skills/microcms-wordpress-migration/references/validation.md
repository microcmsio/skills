# 品質チェックと報告書

登録が終わったら、引き継ぎ前にデータ移行の検証を行う。新サイトの実装・リダイレクト設定・本番切り替え後の確認は別作業として担当者へ引き継ぎ、データ移行の完了条件と分けて記録する。結果は `migration/report.md` に書く。数えられるものはスクリプトで数え、目で見るのはスクリプトで判断できないものだけにする。

## チェック一覧

### 件数

- [ ] 書き出したデータの件数が、移行元の件数と一致する。書き出しの警告（`wxr-warnings.json` など）が空か、残っている警告の扱いが決まっている（`general.md` の 3）
- [ ] 移行元の種類ごと・公開状態ごとの件数と、microCMS の件数（`totalCount`）が一致する。差があれば、その内訳（意図して移さなかったもの、失敗したもの）を全部説明できる
- [ ] 移さないと決めた種類（添付ファイル投稿、メニュー項目、リビジョン、フィールド定義など）が、意図どおり除外されている

- [ ] 既存 ID は計画で採用した識別情報がすべて移行元と一致したものだけ更新され、衝突は失敗として記録されている
- [ ] 登録後のメタ情報で公開・下書き・公開終了の状態が計画と一致している。予約設定や自動処理できない状態の扱いが決まっている

### 取り出しと登録前の確認

- [ ] 種類ごとの識別方法と対応表があり、代替キーを使う場合も一意性を確認している
- [ ] オプションページの現在値・取得元・確認範囲が記録され、未取得の値を空値で上書きしていない
- [ ] 入れ子を含む繰り返しフィールドの型を検査し、空値の更新には `[]` を使っている
- [ ] 継続した 504 があれば、原因の切り分け・修正後の全フィールドでの確認結果、または未解決事項を記録している

### 選択系フィールド

- [ ] 単一／複数選択・真偽値への対応と、value の保持要否が計画に記録されている
- [ ] 元 value・label と移行先の対応表があり、同じ label への意図しない統合や未定義の値の取りこぼしがない
- [ ] 登録後の選択値・参照 ID・真偽値が対応表と一致し、未選択も意図どおりに反映されている

### 本文

- [ ] 許可した要素（`richeditor.md` の表）以外のタグが残っていない
- [ ] 移行元のドメインの画像 URL（`/wp-content/uploads/`）が残っていない
- [ ] 展開できないショートコードの元記法・対象が記録され、未解決のものは本文登録を保留し報告している
- [ ] ショートコード（`\[[a-zA-Z0-9_-]+`）が残っていない（意図して残したものを除く）
- [ ] Gutenberg のブロックコメント（`<!-- wp:`）が残っていない
- [ ] `[object Object]`、`undefined`、`NaN`、CDATA、未デコードの HTML エンティティが残っていない
- [ ] 内部リンクが合意済みの新サイトのパスになっている。新 URL が未確定のリンクは一覧で引き継いでいる
- [ ] 送った本文と、登録後に GET した本文を比べ、黙って消された部分がない（タグを除いたテキストの長さ、画像・リンク・表の数。`richeditor.md` の「変換の進め方」）

### 参照とメディア

- [ ] 参照フィールドの ID がすべて実在するコンテンツを指している
- [ ] 後入れした自己参照・相互参照のフィールドと、登録後の参照値が対応表に一致している。双方向を持つ場合は計画した関係を照合している
- [ ] 画像・ファイルのフィールドがすべて microCMS の URL になっている
- [ ] アップロード時にファイル部分の MIME タイプを指定し、画像が `images.microcms-assets.io` の URL で登録されている（ファイル扱いの `files.microcms-assets.io` になっていない）
- [ ] アイキャッチが付いていた記事の数と、microCMS で画像が入っている記事の数が一致する
- [ ] `wp-content/uploads` になかったファイル（移行元でも消えていたもの）と、uploads 以外の URL（外部サービス、CDN）が一覧になっていて、扱いが決まっている
- [ ] 同じ旧 URL で差し替えた画像は対象を明示して再アップロードし、本文・画像フィールドへ新 URL が反映されている
- [ ] メディアの未解決一覧は再試行しなかった項目も含めて保持されている。非ゼロの終了コードで報告した未解決項目を報告書に載せている
- [ ] 5MB を超えて圧縮してから上げた画像が一覧になっている
- [ ] API で上げられなかったメディア（画像以外の 5MB 超えなど）が一覧になっていて、手で上げる担当が決まっている

### サイズ

- [ ] サイズの上限で登録に失敗したコンテンツが、`report.md` の「失敗したもの」に載っている（1 コンテンツ約 200KB の保存サイズは事前に測れない。`microcms.md` の 6 章）
- [ ] 本文が 90KB を超え、PATCH で更新できないコンテンツの一覧がある（案件用スクリプトの登録前検査ログ）

### 目で見る

- [ ] 種類の違うコンテンツ（クラシック、Gutenberg、ページビルダー、カスタム投稿タイプ）から 5 件以上を、microCMS の管理画面で旧サイトの本文と見比べた
- [ ] 旧サイトの本文の表示にあって、DB の本文には無かった内容（`wordpress.md` の 6 章）の扱いが決まっている

### URL

- [ ] 旧 URL → 新 URL のリダイレクト表（CSV：`from,to,status`）がある。移行元の全公開 URL が載っている。新 URL が未定のものは未確定として引き継いでいる
- [ ] 新サイトでのリンク・リダイレクトの動作確認を、別作業として担当者へ引き継いでいる
- [ ] 移行対象の canonical・SEO タイトル・説明文が microCMS の対応フィールドに入っている（新規は空値を省略し、更新は型に応じた空値で古い値を消している）

## report.md の形

読む人が上から順に「どうなったか → 何が失敗したか → 次に何をするか」をつかめるようにする。件数はログ（`logs/upsert-results.ndjson`、`logs/transform-warnings.ndjson`、`media-skipped.json` など）から集計し、手で数えない。

登録ログは再実行で追記されるため、行数や過去の成功・失敗をそのまま足さない。

- ログはサービスごとに分ける（例：`logs/<service>/upsert-results.ndjson`）。集計するサービスと対象ログをレポートに明記する。別サービスのログが混在し、書き込み先を判別できない場合は集計に使わない。
- 今回の移行対象に含まれる endpoint・ID に絞り、サービス・endpoint・ID ごとに最後に記録された結果を採用する。失敗後に更新成功した同じ ID は「登録済み」1 件とし、以前の失敗を現在の失敗に加算しない。新規作成と更新も、同じ ID を重複計上しない。
- 変換警告やメディアの未解決一覧は、今回の入力と対応状況を突き合わせ、解決済みの警告を現在の要対応として数えない。最終的な件数・公開状態は移行先の取得結果とも照合する。

`raw/` やログのパスは固定値ではない。以下のテンプレートには、今回の集計・検証で実際に使ったファイルを記録する。再取得で `raw-final/` を使った場合は、その中の警告を参照し、初回の `raw/` の警告と取り違えない。

- **失敗**：直さないと切り替えられないもの（登録の失敗、件数の不一致、参照先のないもの）
- **要対応**：登録はできたが人の確認や手直しが要るもの（変換できなかった書式、手で上げるメディアなど）。切り替え後でもよいものは優先度を下げる

状態の 1 行は、失敗が 1 件でもあれば ❌、失敗はなく要対応があれば ⚠️、どちらもなければ ✅ にする。

```markdown
# 移行レポート：<移行元> → microCMS <サービス名（サービスID）>
実行日時：YYYY-MM-DD HH:MM ／ 状態：✅ 完了 | ⚠️ 要対応あり | ❌ 失敗あり
対象サービスID：<実際のサービスID>
集計対象：<今回の移行対象一覧のファイルと、使用した登録ログのパス>

## 1. 結果のまとめ
| 種類 | 移行元 | 登録済み | 失敗 | 移さない | 要対応 |
|---|---|---|---|---|---|
| （種類ごとに 1 行） | | | | | |
| 合計 | | | | | |

## 2. 失敗したもの（直さないと切り替えられない）
| コンテンツ ID | 旧 URL | 何が起きたか | 対応案 |
|---|---|---|---|

## 3. 人がやること（優先度順）
| 優先度 | やること | 対象 | 件数 | 担当 |
|---|---|---|---|---|

## 4. 移していないもの（意図したもの）
| 種類 | 件数 | 理由 | 決めた人・日付 |
|---|---|---|---|

## 5. チェック結果
（この文書のチェック一覧を ✅ 通過 ／ ❌ 不合格 ／ ⏭ 対象外 で並べる。❌ には 2 章か 3 章の該当行を示す）

## 6. 切り替えまでの残り作業
- [ ] 最新の移行元データでの流し直し
- [ ] フロントエンド担当者への引き継ぎ（スキーマ・URL 対応表・未解決事項）
- [ ] 別作業：新サイトの実装、リダイレクト設定・動作確認、本番切り替え
- [ ] 移行のために実際に停止した Webhook の再開（対象・担当・タイミングを記載。停止していなければ対象外）

## 7. 後片付け
- [ ] WordPress のサーバーに移行用のアカウントを発行していれば、無効にする
- [ ] microCMS の移行用 API キーを削除する
- [ ] 試験用に作った API・コンテンツ・メディアを片付ける（API の削除は管理画面から）
- [ ] 一時的に増やした API があれば、管理画面で削除してもらう（削除すると追加料金は日割りで止まる）

## 付録

- 移行元データ：<今回使用した WXR・uploads のパス。分割ファイルはすべて記載>
```
