# 移行の進め方

時間がない・リスクが高い案件は 2 段階に分けてもよい。まず旧サイトに近い形で移して欠落がないことを確かめ、そのあとでスキーマを整理し直す。

## 流れ

### 0. 事前確認

現在の作業に必要な項目を確かめ、結果を `plan.md` の冒頭に書く。手元の WXR・uploads の棚卸しや変換方針の検討には、API キーや MCP 接続は不要。接続情報がなくてもローカル調査を進め、移行先の既存 API・件数・権限などは「接続後に確認」と記録する。移行先の状態やプランに依存する設計は仮案として示す。

microCMS に接続する段階で接続情報とサービスを確認し、書き込み前には必要な権限・プラン・計画の承認を揃える。

| 確認すること | 方法 | 問題があったとき |
|---|---|---|
| コマンドの実行の可否 | 人に聞く。WP-CLI、Node、本番サーバーへの SSH や `curl` などを実行してよいか | 実行できないものは、人に実行してもらう手順に切り替える |
| 必要なツール | 選んだ実行環境のバージョン、`wp --info` など、使う予定のものだけ | 足りないものを入れてもらう |
| データの受け取り方 | `wordpress.md` の 0 章（既定は WXR と `wp-content/uploads` をファイルでもらう。足りないときだけテーマのコードや WP-CLI） | もらえないものは、公開ページから読み取るか、移す範囲を人と決め直す |
| 接続情報（microCMS に接続するとき） | `.env` の各項目が設定済み／空／未設定か（値は表示しない） | 足りないものを入れてもらう。ローカル調査は続けてよい |
| 書き込み先のサービス（microCMS に接続するとき） | `GET https://<service>.microcms-management.io/api/v1/service` でサービス名を取り、人に「このサービスでよいか」を確認する | 違えばそのサービスへの操作を止める |
| **microCMS の MCP の接続先** | MCP のツールがあれば、MCP の接続設定やサービス情報でサービスID（サービスドメイン）を確認し、`MICROCMS_SERVICE_DOMAIN` と完全一致することを確かめる。ツール名やAPI一覧の一致だけでは証明にならない（空のサービス同士でも一致する） | **一致を確認できなければ MCP で書き込まない**。読み取りツールに識別情報がなく、接続設定も確認できない場合は、確認済みの `.env` を使うスクリプトへ切り替える。MCP は接続した 1 つのサービスしか操作できず、`.env` と別のサービスにつながっていることがある |
| 契約中のプラン | 人に聞く（API では取れない） | わかるまで、プランに依存する設計を決めない（下の「前提が変わったら」） |
| 書き込みの経路 | 件数と MCP の有無から、スクリプトか MCP かを決める | — |

### 1. 棚卸し

書き込みの前に、次を数字つきで把握する。

- どうやってデータを取れるか（WXR、`wp-content/uploads`、テーマ・プラグインのコード、公開 HTML、必要なら DB ダンプ）。手元にないものは推測せず、依頼者に頼む。
- 種類ごとの件数（投稿タイプ別、公開状態別、言語別）
- 本文の形式（Gutenberg / クラシック / ページビルダー / カスタムフィールド）
- メディアの枚数と合計サイズ、5MB を超えるものの数
- 種類どうしの関係（カテゴリ、著者、関連記事、カスタムフィールドの参照）
- コメント、ユーザー、メニューを移すかどうか
- 新サイトで残す必要のある URL

**移行先の microCMS サービスも棚卸しする。** マネジメント API の `GET https://<service>.microcms-management.io/api/v1/apis` で既存の API（エンドポイント）一覧を取り、移行で使う名前とぶつからないか確かめる。既存の API がある場合は、そのサービスが本番か検証用か、既存の API を使うのか新しく作るのかを人に確認する。

### 2. 対応表を決めて `plan.md` に書く

`plan.md` は次の形で書く。人が最初の表だけ読めば判断できるようにする。

```markdown
# 移行計画書：<移行元> → microCMS <サービスID>
- 状態：承認待ち

## 事前確認の結果（上の表の形。仮の前提で進めた項目には「仮」と書く）

## 既定の扱いで進めるもの（下の「既定の扱い」のうち、この案件で当てはまったもの。変えたい場合だけ指示してもらう）
| 対象 | この案件での扱い | 件数・対象 |

## 0. 先に決めてほしいこと（既定の扱いがないもの、既定が合わなそうなものだけ）
| # | 何が起きているか | 選択肢 | 推奨 |

## 1. 棚卸し（移行元のアクセス手段・件数・本文の形式、移行先サービスの現状）
## 2. 移行先のスキーマ（API ごとのフィールド対応表）
## プランの確認（plans.md の形。上限・判定・超過時の費用と代わりの案）
## 3. 移さないもの（と理由）
## 4. 変換のルール（本文・ショートコード・メディア・公開状態。既定の扱いから変えたものもここに書く）
## 5. ID の付け方
## 6. 実行の順番と所要時間（回数制限から計算する）
## 7. URL 対応表（旧 URL → 合意済みの新 URL。未定なら未確定と記録）
## 8. フロントエンド担当者への引き継ぎ（実装・リダイレクト設定・本番切り替えは対象外）
```

**ここで人の承認をもらう。**

承認のあと、**API を作る直前にも、作る API とフィールドの一覧（最終版）を見せて確認する**（作ったあとはマネジメント API で変更できない）。承認後に計画を少しでも変えた場合は、変えた点をはっきり示す。

### 3. 取り出す

移行元のデータを `raw/` にそのまま保存する。変換は取り出しと分ける。WXR の再変換では出力先を `raw-final/` など別の空ディレクトリにし、後続の変換スクリプトの入力も切り替える。古い投稿タイプの JSON が最新データに混ざらないよう、空でない出力先を拒否するか実行ごとに出力先を分ける。投稿タイプごとに分けた WXR も、それぞれ別の出力先で変換してから統合する。

取り出したら、**取り出しが完全だったかを確かめる。** WXR のエクスポートが途中で切れていたり（ファイルの末尾が `</rss>` で終わっていない）、一部の種類だけ入っていなかったりしても、エラーにならないことがある。

- 種類ごと・状態ごとの件数を、移行元の件数（管理画面の投稿一覧に出る件数、`wp post list --format=count` など）と突き合わせる
- 空のファイルや、件数 0 の種類がないか見る
- 書き出しの警告（戻せなかったシリアライズなど）を確かめる（今回の出力先に保存した警告ログ）

今回使う WXR・uploads・書き出し先・警告ファイルの実際のパスを `plan.md` に記録し、`report.md` にも引き継ぐ。分割した WXR を統合した場合は、元ファイルと各出力先もすべて記録する。

合わないものは `logs/` に記録し、`plan.md` か `report.md` で人に知らせる。

### 4. 変換する

`raw/` から microCMS の形の JSON を作って `transformed/` に置く。変換できなかったもの・怪しいものは、コンテンツごとに `logs/transform-warnings.ndjson` に 1 行ずつ書く（ID、フィールド、何が起きたか、元の値の抜粋）。

最初は種類の違う 3〜5 件だけ変換して、人と一緒に中身を見る。全件はそのあと。

### 5. 登録する

参照フィールドは、参照先のコンテンツが先にないと登録できない。次の順に登録する。

1. メディア→ 本文と画像フィールドの URL を置き換える
2. 参照される側（カテゴリ、タグ、著者など）
3. 本体（記事、固定ページ、カスタム投稿タイプ）
4. 本体どうしの参照（関連記事など）と、内部リンクの書き換え

登録スクリプトは `scripting.md` の実装指針に従って作る（件数が少なければ microCMS の MCP で直接入れてもよい）。

### 6. 検証する

`validation.md` のチェックを全部やり、`report.md` を書く。会話での報告は `SKILL.md` の「最後の報告」の形にする。

### 7. 引き継ぐ

スキーマ、変換ルール、旧 URL の対応表、未解決事項をフロントエンド担当者に渡す。新 URL が未定なら対応表に未確定と記録し、推測で本文リンクを書き換えない。新サイトの実装、リダイレクトの設定、本番切り替え・監視は担当者の別作業とする。Next.js の実装には `microcms-nextjs` を案内する。切り替え直前の最終データ投入が必要なら、最新の移行元データで 3〜6 を再実行する範囲とタイミングを計画に残す。

## 既定の扱い（聞かずに決めるもの）

正解がほぼ決まっているものは、人に聞かずに次のとおり進める。ただし黙っては決めない。`plan.md` の「既定の扱いで進めるもの」に、この案件で当てはまったもの（件数・対象）を書き、変えたい場合だけ指示してもらう。案件の事情で既定が合わないと気づいたとき（右の列）は、既定で進めずに「先に決めてほしいこと」に載せる。

| 対象 | 既定の扱い | 既定が合わない例 |
|---|---|---|
| 日付 | WP で表示されていた日時（`post_date`）を、新サイトの表示用のタイムゾーン（指定がなければ Asia/Tokyo）の時刻として解釈し、UTC に直して入れる。WP のタイムゾーンが UTC のままでも、サイトに出る日付が変わらない。`post_date_gmt` は使わない | 海外向け・多言語のサイト（表示用のタイムゾーンを確認する）。`post_date` と `post_date_gmt` の差が記事によってばらばら（途中で設定を変えた） |
| 5MB を超える画像 | 縮小・再圧縮して 5MB 未満にし、API で上げる。圧縮の道具は実行環境に合わせる。一度流すと `media-skipped.json` に出るので、旧 URL と圧縮後のローカルパスの対応を入力に記録して再実行する。元のファイルは残し、圧縮したものの一覧を `report.md` の付録に載せる。画像以外のファイルや、圧縮しても収まらないものは、手で上げる一覧に出す | 写真・作品が売りのサイト、原寸のダウンロードを提供しているサイト |
| 長い記事 | 事前に分けたり聞いたりせず、そのまま登録する。サイズの上限で失敗したものはログに残り、`report.md` の「失敗したもの」に出る | — |
| 下書き・非公開の記事の日付 | 残さない。公開済みの記事は `publishedAt` に入れ、予約投稿は予約公開の日時に使う | 下書きの作成日を運用で使っている |

## ID の付け方

移行元の ID から決まる ID にする（例：`post-123`、`page-45`、`works-678`、`cat-12`）。コンテンツ ID は 1〜50 文字。

流し直しても重複せず、参照フィールドの値（`cat-12` など）を登録前に決められる。

移行元の ID・旧 URL は専用フィールド `legacyId`・`legacyUrl` にも入れ、入力の `identity` に同じ値と型で指定する。更新前に既存データの両方と照合する。ID が同じでも一致しないもの・識別情報がないものは更新しない。衝突はログに記録し、別 ID を割り当てて参照・URL対応表を更新するか、既存コンテンツを採用するかを人に判断してもらう。移行対象だと推測して上書きしない。識別情報を消すのは流し直しが不要になってから。

## 前提が変わったら

契約中のプラン、移行の対象範囲、データの受け取り方など、設計の前提になる情報がわからないまま、推測で設計を決めない。どうしても先に進める必要があるときは、`plan.md` に「仮の前提」として書き、その前提に依存する設計（API のまとめ方など）を明示する。

前提がわかった、または変わったときは、**承認済みの計画でもそのまま実行しない。** その前提に依存していた設計を見直し、変わる点を示して承認を取り直す。例えば、API 数の上限を低く見積もって API をまとめていたなら、上限に余裕があるとわかった時点で、分ける設計に戻すかを確認する。

## 流し直しのルール

- 変換スクリプトは同じ入力から同じ出力を作る（日時やランダム値を出力に混ぜない。配列の並び順も固定する）
- 新規作成では空の値を省略する。更新（PATCH）で省略したキーは「既存値を維持」であり、空にはならない。変換で管理するフィールドが空になったら、フィールド型ごとの空値を明示する（`microcms.md` の空値表）。手直しを保護するフィールドは送らない。カスタムは更新する子フィールドを指定し、繰り返しは各行の全フィールドを含める。
- メディアは対応表を使い回し、同じファイルを二度上げない。同じ旧 URL の画像を更新した場合は、その URL のみを対象に明示的な再アップロードを行う。旧メディアは削除せず、対応表と本文・画像フィールドを更新する。未解決一覧は再実行でも保持し、成功した URL だけ除く。
- 移行後に人が管理画面で手直しした本文（埋め込みを入れたものなど）は、本文ごと流し直すと消える。手直しを始めたコンテンツは、流し直しの対象から外す（本文を送らない PATCH なら手直しは残る）

## 人に任せること

- `plan.md` の承認
- スキーマの組み直し方、タクソノミーの整理、多言語の持ち方の判断
- 全件投入や削除のように、取り消しにくい操作の実行タイミング
- 変換できなかったものの最終的な扱い
- 生成したスキーマとスクリプトの確認
