# 案件用の移行スクリプトを作る指針

棚卸し、承認済みのフィールド対応表、実データを基に実装する。実行言語と依存パッケージは案件の環境に合わせる。API の仕様・制限・状態遷移は `microcms.md`、本文の変換範囲は `richeditor.md` を参照し、実装時に最新の公式情報を確認する。

## 処理と入出力

取り出し、メディア、変換、登録、検証を分け、途中の成果物から再開できるようにする。

| 処理 | 入力 | 出力・実装上の条件 |
|---|---|---|
| 取り出し | WXR など受領したデータ | 投稿タイプ別の未変換 JSON、種類・公開状態別の件数、復元できなかった値の警告。受領ファイルは変更せず、実行ごとに空の出力先を使う |
| メディア | 添付情報、本文の画像 URL、uploads | サービス別の旧 URL → 新 URL 対応表と未解決一覧。ローカルファイルを優先し、URL から取得する場合は取得失敗も記録する |
| 変換 | 未変換 JSON、対応表、スキーマ | 登録用 JSON、参照 ID の対応表、変換警告。未対応の値を黙って捨てない |
| 登録 | 登録用 JSON、接続先、期待する公開状態 | コンテンツごとの登録結果。存在・識別情報を確認し、本文と公開状態を別操作で反映する |
| 検証 | 今回の移行対象、ログ、登録後の取得結果 | `validation.md` に沿う差分と報告書。成功レスポンスだけで完了にしない |

### 登録データの契約

形式は案件で決めてよいが、少なくとも登録先 endpoint、決定的なコンテンツ ID、期待する公開状態、移行元の識別情報、送信するフィールド値を持たせる。例えば次のように分ける。

```json
{
  "endpoint": "posts",
  "id": "post-123",
  "status": "draft",
  "identity": {"legacySource": "old-site", "legacyType": "post", "legacyId": "123"},
  "content": {
    "legacySource": "old-site",
    "legacyType": "post",
    "legacyId": "123",
    "legacyUrl": "https://old.example.com/post/123/",
    "title": "記事タイトル",
    "body": "<p>本文</p>"
  }
}
```

`identity`・`status` などの制御情報は本文ペイロードへ混ぜない。識別情報は `content` と値・型を一致させ、スキーマにも保存先を作る。更新前には `general.md` の「ID の付け方と識別情報」で採用したキーをすべて照合する。元 ID が取れない場合は一意性を確認した代替キーを使い、旧 URL は任意とする。オブジェクト形式 API は ID を持たないため別処理にし、管理画面での初回保存と対象確認が済んでから endpoint 単位で PATCH する。識別情報、検査、結果ログ、再開方法はリスト形式と共通の方針にする。

## 再実行と失敗の扱い

- 同じ入力から同じ ID・変換結果を作る。入力一覧で endpoint・ID の重複と参照先の欠落を検出する。
- WXR は XML パーサーで読み、名前空間・CDATA・エンティティを扱う。PHP シリアライズはコードを実行せず解析し、復元に失敗した元値と位置を警告に残す。postmeta の重複・順序を保持し、フィールド定義の復元と投稿値の変換を分ける。大規模データは分割かストリーム処理、マルチサイトはサイト単位で処理する。
- メディア対応表は成功のたびに安全に保存し、再開時に再利用する。同じ旧 URL の差し替えは対象を明示して再アップロードし、本文と画像フィールドを再変換する。未解決一覧は今回再試行しなかった項目も保持し、解決したものだけ除く。圧縮後のパスと元ファイルを追跡できるようにする。
- メディア送信時はファイル部分に正しい MIME タイプを付け、画像が画像用 URL で返ることまで確認する（`microcms.md` の 5 章）。圧縮・形式変換した場合は、変換後の実データに合わせて MIME タイプとファイル名も更新する。
- Content API とマネジメント API の制限を分けて待機する。同じサービスを複数プロセスで処理する場合は制限を共有するか直列化する。429・一時的な 5xx は待機して有限回再試行し、上限後は失敗として残す。同じ入力で 504 が続く場合は、`microcms.md` の「504 が続くときの切り分け」へ進む。
- 通信のタイムアウトで書き込み結果が不明な場合は、移行先を取得して確認してから再実行する。PUT の 400 を理由に自動で PATCH に切り替えない。
- 本文・公開状態・公開日時を別々に記録し、最後に取得した状態が期待と一致したものだけ成功にする。未対応の状態や ID 衝突は自動で削除・再作成しない。
- ログにはサービス、実行 ID、endpoint、コンテンツ ID、処理段階、結果、失敗理由を含める。認証情報は含めない。失敗・未解決が残る実行は非ゼロの終了コードとし、報告書に一覧を載せる。

## 書き込み前と登録後の検証

書き込まない検査モードを用意する。スキーマに沿って入れ子まで検査し、送信する `repeater` が配列以外（`null` を含む）なら登録前にエラーにする。更新で空にする場合は `[]` を生成し、すべての空値を一律に `null` にする変換を避ける。ローカル検査では必須値、型、識別情報の一致、ID・参照の整合性、送信 JSON の UTF-8 バイト数を調べる。作成と更新ではサイズ上限が異なるため両方を判定する。接続先を読み取る検査は区別し、ID 衝突・公開状態・権限を確認できた範囲を報告する。

本番投入前には代表的な実データと通信の代替処理で、重複作成の防止、ID 衝突の拒否、空値更新、メディアの再開、429・タイムアウト・状態変更途中の失敗を確認する。その後、承認された接続先で少数を登録し、取得した本文・参照・メディア・公開状態を照合する。実際の実行コマンド、必要な環境変数、再開方法、ログのパスを案件の `plan.md` に残す。
