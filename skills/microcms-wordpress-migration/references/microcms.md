# microCMS のスキーマと API の制約

2026 年 10 月時点の公式ドキュメントと、microCMS への確認に基づく。主な出典は、制限事項（https://document.microcms.io/manual/limitations）と、マネジメント API の API 作成（https://document.microcms.io/management-api/post-apis）。数値は変わることがあるので、気になるものは公式ドキュメントで確認する。`microcms-docs` スキルが使えればそれを使う。使えなければ、ページの URL の末尾に `.md` を付けて取得する（一覧は https://document.microcms.io/llms.txt。存在しないページでも 200 で HTML が返るので、Markdown でなければそのページは無効）。

## 1. API の作り方

- マネジメント API で作れる。microCMS の MCP サーバーが接続されていれば `microcms_create_api` が使える。管理画面の「APIスキーマのインポート」（JSON）でもよい。
- **形式は 2 種類**：リスト形式（記事など複数件）とオブジェクト形式（サイト設定など 1 件）。書き込み API（POST / PUT）はリスト形式だけ。オブジェクト形式は PATCH で更新する。
- 参照フィールドは、**参照先の API が先に存在しないと作れない**。作る順番はカテゴリ・著者 → 記事。
- **API の削除と、作成済みの API の変更はマネジメント API でできない**（できるのは一覧・取得・作成だけ）。作り直すには管理画面で人に削除してもらうので、作る前に最終版を確認する。
- 作る前に、既存の API 一覧（`GET https://<service>.microcms-management.io/api/v1/apis`）とエンドポイント名がぶつからないか確かめる。
- プランの API 数の上限を超えると 402 が返る。上限と追加料金は料金ページから毎回取得して確かめる（`plans.md`）。追加料金を許可するかは必ず人に確認する。
- オブジェクト形式の API（サイト設定など）は ID を持たない 1 件だけのコンテンツ。**最初の 1 件は API で作れない**（PUT は「PUT is forbidden」、PATCH は「Content is not exists」になる）。API を作ったら、管理画面で一度保存してもらい、そのあと `PATCH /api/v1/<endpoint>` で中身を入れる。登録処理はリスト形式と分けて実装する。人に保存を頼む作業を `plan.md` の実行の順番に入れる。

## 2. フィールドの対応表

| WordPress | microCMS（`kind`） | 書き込む値 |
|---|---|---|
| タイトル、スラッグ、短いテキスト | `text` | 文字列 |
| 抜粋、改行ありのテキスト | `textArea` | 文字列（改行は `\n`） |
| 本文、WYSIWYG | `richEditorV2` | HTML 文字列（`richeditor.md` の範囲だけ） |
| アイキャッチ、画像フィールド | `media` | **同じサービスにアップロード済みの** URL |
| ギャラリー | `mediaList` | URL の配列（最大 100） |
| ファイル | `file` | アップロード済みの URL（使えるプランが限られる。`plans.md`） |
| 日付 | `date` | ISO 8601 |
| 数値 | `number` | 数値 |
| 真偽値 | `boolean` | `true` / `false` |
| 選択肢（固定の値） | `select` | 選択肢の値の配列 |
| カテゴリ、タグ、著者、投稿オブジェクト | `relation` / `relationList` | 参照先のコンテンツ ID（の配列） |
| グループ | `custom` | `{ "fieldId": "<カスタムフィールドID>", ... }` |
| リピーター、フレキシブルコンテンツ | `repeater` | 上の `custom` の配列。行ごとに `fieldId` でレイアウトを選ぶ |
| SEO 項目のまとまり | `custom`（`seo` など） | 同上 |
| 外部サービスのデータ | `iframe`（拡張フィールド） | 設定したいプロパティだけのオブジェクト |

**タクソノミーは、WordPress の 1 種類につき microCMS の API を 1 つにする**（カテゴリ → `categories`、タグ → `tags`、カスタムタクソノミー → それぞれ別の API）。複数の種類を 1 つの API にまとめると、カテゴリを選ぶ欄にタグなど別の種類のタームまで並び、フロントエンドでも毎回種類で絞り込むことになる。まとめるのは、人がこの欠点を理解して選んだときだけにする。階層のあるカテゴリの親子関係は、同じ API を参照する `relation` フィールド（`parent`）で表す。**自分自身の API を参照するフィールド（`parent` など）は、マネジメント API では作れない**。API を作ったあと、管理画面で人に足してもらう。その作業と、足したあとに親子関係を入れ直す手順を `plan.md` に入れる。

カテゴリ・タグ・著者を別 API にするか `select` にするかなど、移行に限らないモデリングの考え方は、`microcms-guide` スキルのコンテンツモデリング（https://github.com/microcmsio/skills/blob/main/skills/microcms-guide/references/content-modeling.md）を参照する。

フレキシブルコンテンツは、レイアウト 1 つにつきカスタムフィールド 1 つを作り、それらを全部 `customFieldIds` に入れた `repeater` で表す。書き込みは次の形。

```json
{
  "sections": [
    { "fieldId": "sectionText", "heading": "課題", "body": "<p>…</p>" },
    { "fieldId": "sectionImage", "image": "https://images.microcms-assets.io/…", "caption": "…" }
  ]
}
```

## 3. フィールド定義の制約

- `endpoint`：3〜32 文字、`a-z0-9-_`、サービス内で重複不可
- `fieldId`：2〜20 文字、`a-zA-Z0-9-_`。`id`・`createdAt`・`updatedAt`・`publishedAt`・`revisedAt`・`fieldId` は大文字小文字を問わず使えない。WP のフィールド名が長いとき・予約語のときは名前を変え、`plan.md` の対応表に残す。
- **カスタムフィールドの中にカスタムフィールドは入れられない**（`repeater` は入れられる）。つまり「繰り返し → カスタム → 繰り返し → カスタム」までが限界。それより深い ACF の入れ子は平らにする。
- マネジメント API で API を作るとき、カスタムフィールド（`customFields`）は 1 API につき 99 件まで。繰り返しフィールドの構造によっては、保存時に「スキーマのフィールド数が上限を超えています」になることがある。
- 一意制約（`isUnique`）は `text` だけ、1 API につき 5 個まで。投稿のスラッグに付けると重複を防げる。固定ページは親が違えば同じスラッグがあり得るので付けない。
- `select` の選択肢の ID は、半角英数字・`_`・`-` からなる 10 文字（省略すれば自動生成）。
- コンテンツ ID は 1〜50 文字（`post-123` の形は使える）。

## 4. 書き込み API

エンドポイント：`https://<service>.microcms.io/api/v1/<endpoint>`、ヘッダーは `X-MICROCMS-API-KEY` と `Content-Type: application/json`。API キーには、使う書き込みの権限が要る（移行では PUT・PATCH、流し直しと後片付けで DELETE）。権限の一覧は `SKILL.md` の「接続情報」。

| | 動き | 本文の上限 |
|---|---|---|
| `POST /<endpoint>` | 新規作成。ID は自動 | 約 300KB |
| `PUT /<endpoint>/<id>` | **ID を指定して新規作成**。既にある ID だと 400 | 約 300KB |
| `PATCH /<endpoint>/<id>` | 既存コンテンツの一部を更新 | **約 90KB** |
| `DELETE /<endpoint>/<id>` | 削除 | — |

- マネジメント API のコンテンツ詳細で存在確認する。404 のときだけ `PUT` で作成する。既存なら本文を取得し、`identity` の `legacyId`・`legacyUrl` と両方一致したものだけ `PATCH` で更新する。PUT の 400 から PATCH へ自動で切り替えない。
- **PATCH の上限は PUT より小さい**。本文が 90KB を超えるコンテンツを流し直すと、更新で失敗する。そのときは削除してから PUT し直すしかない（削除は人に確認してから）。
- 書き込みで省いたフィールドには、スキーマの初期値は入らない。
- リッチエディタで使えない書式を送っても、エラーにならずに 201 / 200 が返り、その部分だけ消える（`richeditor.md`）。
- 画像・ファイルの URL は、同じサービスにアップロードしたもの以外は弾かれる。

### 空値と更新

新規作成では空値を省略できるが、PATCH で省略すると既存値が残る。変換で管理するフィールドを空にする場合は、次を明示する。`false`・`0` は空値ではない。

| フィールド | PATCH で空にする値 |
|---|---|
| テキスト、テキストエリア、リッチエディタ、画像、日時、ファイル | `""` |
| 数字、真偽値 | `null` |
| 複数画像、セレクト、複数コンテンツ参照、繰り返し | `[]` |
| コンテンツ参照、カスタム、拡張フィールド | `{}` |

カスタムフィールドを部分更新する場合は `fieldId` と更新対象の子フィールドを送り、繰り返しフィールドは各行の全フィールドを送る。[公式PATCH仕様](https://document.microcms.io/content-api/patch-content)を参照する。変換スクリプトで型ごとに指定する。

## 5. メディア

- マネジメント API：`POST https://<service>.microcms-management.io/api/v1/media`、`multipart/form-data` の `file` に 1 ファイル。
- **1 回 1 ファイル、5MB まで**。画像なら縮小・再圧縮して 5MB 未満にし、API で上げる（`general.md` の「既定の扱い」）。画像以外や、圧縮しても収まらないものは管理画面から手で上げる。自動処理できないものは別リストに出す。
- 画像以外のファイルは、使えるプランが限られる（`plans.md` で確かめる）。
- 返ってくる URL は `images.microcms-assets.io`（画像）か `files.microcms-assets.io`（ファイル）。
- 画像の代替テキストはメディアには持てない。本文中なら `img[alt]`、画像フィールドなら別の `text` フィールドに入れる。

## 6. 回数・サイズの制限

| 対象 | 制限 |
|---|---|
| 書き込み（POST / PUT / PATCH / DELETE） | 1 サービスあたり毎秒 5 回 |
| 読み取り（GET） | 毎秒 60 回 |
| マネジメント API（メディア、API 作成など） | IP ごとに 10 秒で 10 回（ベータのため変わる可能性あり） |
| 1 コンテンツの保存サイズ | 約 200KB（公開と下書きの両方を持つと約 400KB） |
| リクエスト URL | 8KB |

サイズの制限は 2 種類あり、計算方法が違うので混ぜない。

- **リクエストの大きさ**（PUT / POST 約 300KB、PATCH 約 90KB）：送る JSON のバイト数。`Buffer.byteLength(JSON.stringify(content))` で正確に測れる。登録前の検査に組み込む。日本語は UTF-8 で 1 文字約 3 バイトなので、文字数で見積もらない。
- **保存サイズ**（1 コンテンツ約 200KB、公開と下書きの両方で約 400KB）：内部の構造で数えるので、**事前には測れない**。JSON のバイト数から推定しない。収まらなければ登録が失敗するので、失敗をログに残して `report.md` に出す。

制限以内でも 429 や 5xx が返ることがあるので、再試行は必須。429 のときは `X-RateLimit-Reset` を見て待つ。

所要時間の目安：記事 3,000 件なら書き込みだけで約 10 分、画像 3,000 枚ならマネジメント API の制限で約 50 分。

これは書き込み・アップロードだけの目安。存在確認・公開状態変更・状態検証にもマネジメント API を使う場合、総所要時間はさらに長くなる。登録パターンごとのリクエスト数を数え、マネジメント API の待機時間も計画に含める。

## 7. 公開状態と日付

- クエリ `status=draft` で下書き、`status=closed` で公開終了として作れる。省略すると**公開**になる。
- `publishedAt` を送ると公開日を指定できる。ただし**下書きで作るときは指定できない**。
  - 公開済みの記事：公開状態で作り、`publishedAt` に WP の公開日を入れる
  - 下書き・非公開の記事：下書きで作る。WP の日付は残さない（`general.md` の「既定の扱い」）
- 予約投稿は `status=draft` で作ったあと、予約公開を設定する（MCP なら `microcms_update_content_reservation`）。**予約を設定したコンテンツは DELETE が 400（content is scheduled）になる**。流し直しや後片付けで削除するときは、先に予約を外す。
- 非公開（private）にあたる状態は microCMS にない。下書きにするか、移さないかを人に確認する。

### 流し直し時の公開状態

本文の PATCH と公開状態の変更は別操作。status 省略の PATCH は下書きを公開せず、公開中への `status=draft` も公開を止めない。

登録スクリプトでは、既存の公開中・下書きを基本的な自動更新対象とする。下書き→公開は下書き本文を更新してから、マネジメント API の `PATCH /contents/<endpoint>/<id>/status` に `{"status":["PUBLISH"]}` を送り、その後 `publishedAt` を設定する。公開中→下書きは `{"status":["DRAFT"]}` で公開を止めてから下書き本文を更新する。新規は下書きで作ってから公開し、公開終了は PUT で直接作る。最後にメタ情報を再取得し、期待した状態と一致した場合だけ成功にする。

公開終了の既存コンテンツ、公開中かつ下書き中、予約設定あり、既存から公開終了への変更は、自動処理せず失敗として記録する。管理画面で状態や予約、残す下書きを確認し、必要な操作をしてから流し直す。自動で削除・再作成しない。API の状態遷移には制限があるため、[公開状態変更の公式仕様](https://document.microcms.io/management-api/patch-contents-status)と[メタ情報の取得](https://document.microcms.io/management-api/get-content)を確認する。

## 8. 環境と Webhook

- 複数環境機能で作った別のサービスには、メディアの URL を持ち越せない。**環境ごとにメディアを上げ直し、対応表も環境ごとに作る**（`media-map.<service>.json` のように分ける）。
- CSV インポートでは Webhook が発火しない。**API での書き込みでは発火する**ので、ビルドが大量に走らないよう、移行中は Webhook を止めてもらう（再開は `report.md` の残り作業）。
